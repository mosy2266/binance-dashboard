# binance-dashboard

바이낸스 실시간 거래 데이터 대시보드입니다. BTCUSDT/ETHUSDT 종목의 시세와 거래 현황을 수집, 저장하여 대시보드로 보여줍니다.

## 1. 실행 방법

프로젝트 루트(`docker-compose.yml`이 있는 위치)에서 아래 명령을 실행합니다.

```bash
docker compose up -d --build
```

- 대시보드: http://localhost:3000
- 백엔드 API: http://localhost:8080 (`/api/tickers`, `/api/klines`, `/ws/market`)

DB가 비어있으면 백엔드가 기동 시 최근 90일치 백필을 비동기로 시작합니다. 대시보드는 백필이 끝나기 전에도 바로 열리고, 데이터는 점진적으로 채워집니다(진행 상황은 `docker compose logs -f backend`로 확인할 수 있습니다).

## 2. 개발 환경

| 구성 요소  | 스택                                                                       |
| ---------- | -------------------------------------------------------------------------- |
| 백엔드     | Java 21, Spring Boot 4.1, Spring Data JPA, JDK 내장 `HttpClient` WebSocket |
| 프론트엔드 | React 19, Vite 8                                                           |
| DB         | PostgreSQL 16                                                              |
| 인프라     | Docker / Docker Compose                                                    |

### 2-1. 별도의 설정이 필요한가요?

해당 Repository를 clone한 뒤 `docker compose up -d --build`만 실행하면 되고, 추가로 설치하거나 설정해야 하는 것은 없습니다.

- 단, Docker(+ Docker Compose)가 설치되어 실행 중이어야 하며, `3000`/`8080`/`5432` 포트가 비어 있어야 합니다.

## 3. 주요 기능 및 구현 내용

- **실시간 시세 수집 파이프라인**: 바이낸스 WebSocket(combined stream)으로 BTCUSDT/ETHUSDT의 1분봉 및 24시간 Ticker를 실시간 수집하고, REST 페이지네이션으로 최대 90일 과거 데이터를 백필합니다.
- **조회 API**: `GET /api/klines`(interval별 롤업 집계), `GET /api/tickers`를 제공합니다.
- **실시간 브로드캐스트**: `/ws/market`으로 신규 캔들 및 Ticker를 프론트엔드에 즉시 push합니다.
- **운영 대시보드**: 심볼별 통계 카드(현재가/변동률/고저가/거래량), 가격 추이 차트(interval 전환, 크로스헤어 툴팁, 표 보기 토글), WebSocket 연결 상태 표시, 라이트/다크 모드를 구현했습니다.
- **배포**: `docker compose up` 한 번으로 DB+백엔드+프론트엔드를 통합 기동하고, 헬스체크 기반으로 기동 순서를 보장합니다.

## 4. 문제 접근 방식

요구사항을 세 층위로 나눠서 접근했습니다.

1. **수집(파이프라인)**: '무엇을, 어떻게 빠짐없이 모을 것인가'라는 문제입니다. 실시간성과 과거 데이터 완전성은 서로 다른 문제라고 보되, 처음부터 실시간 스트림과 과거 백필을 하나의 gap 계산 로직으로 통합 설계했습니다. 이 둘을 별개 기능으로 만들면 최초 기동/재시작 후 복구가 각각 다른 코드 경로를 타게 되어 검증 부담이 커진다고 판단했습니다.
2. **제공(API)**: '저장된 데이터를 어떤 모양으로 노출할 것인가'라는 문제입니다. 저장은 1분봉 하나로 단순화하고, 5m/1h 등 다양한 interval 요구는 조회 시점 집계로 흡수해 쓰기 경로를 단순하게 유지했습니다.
3. **소비(대시보드)**: '사용자가 무엇을 보고 싶어 하는가'라는 문제입니다. 지표를 나열하기 전에 '투자 판단'과 '운영 현황 파악'이라는 두 관점으로 먼저 나누고, 각 지표가 그중 어떤 질문에 답하는지 근거를 남겼습니다.

## 5. 구조 설계

### 5-1. 데이터 파이프라인 설계

```
Binance WebSocket (combined stream)          Binance REST (klines)
        │                                              │
        ▼                                              ▼
BinanceWebSocketClient                    BinanceRestClient + KlineBackfillService
        │                                              │
        └──────────────┬───────────────────────────────┘
                        ▼
         KlineUpsertDao / TickerUpsertDao (upsert)
                        ▼
              PostgreSQL (kline_1m, ticker_24h)
                        ▲
      GapScanScheduler (10분 주기 안전망) ──┘
                        │
        KlineQueryService (조회 시 SQL 집계 롤업)
                        │
              KlineController / TickerController
```

- 저장은 1분봉 하나로 단순화했습니다. `kline_1m` 테이블만 두고, 5m/15m/1h/4h/1d는 조회 시점에 PostgreSQL `date_bin`으로 집계합니다(open=최초값, close=최종값, high=MAX, low=MIN, volume=SUM). 여러 간격을 각각 저장하면 쓰기 경로와 정합성 관리가 심볼×간격 수만큼 늘어나므로, '저장은 최소 단위 하나, 조회 시 집계'로 복잡도를 낮췄습니다.
- Upsert 기반으로 쓰기 경로를 통일했습니다. 백필(배치)과 실시간 갱신(단건) 모두 `INSERT ... ON CONFLICT (symbol, open_time) DO UPDATE` 하나로 처리합니다. JPA `save()`는 백필처럼 대량 행을 처리할 때 매 행 SELECT 오버헤드가 커 사용하지 않았습니다.

자세한 설계 배경과 트레이드오프는 [DATA_PIPELINE_DESIGN.md](DATA_PIPELINE_DESIGN.md)에 정리해두었습니다.

### 5-2. 데이터 백필 방법

| 방법                            | 장기(수주~수개월) 백필 가능 여부                                                   | 채택 여부                              |
| ------------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------- |
| **REST `klines` 페이지네이션**  | 가능 - 임의 과거 구간을 정확히 재구성할 수 있음                                    | ✅ 채택                                |
| WebSocket 재연결 캐치업         | 불가능 - 바이낸스 WS는 재연결 시 과거 메시지를 재전송하지 않음(다운타임 동안 유실) | 순간적 유실 대응 용도로만 병행         |
| 자체 이벤트 로그(Kafka 등) 재생 | 가능하지만 별도 인프라가 필요                                                      | 심볼 2개 규모에 과설계로 판단해 미채택 |

REST 페이지네이션만이 장기 백필 요구사항을 충족하므로 이를 채택했습니다. 최초 기동(빈 DB 채우기)과 재시작 후 누락 복구(장기간 유실 채우기)를 별개 기능으로 만들지 않고, '심볼별 마지막 저장 시각 → 현재'라는 동일한 gap 계산(`GapCalculator`)으로 통합했습니다.

데이터가 없으면 기본 lookback(90일)부터, 있으면 마지막 저장 시각 다음 분부터 시작합니다. 이 로직은 앱 기동 시, WebSocket 재연결 성공 시, `GapScanScheduler`(10분 주기 안전망)가 지연을 감지했을 때 세 지점에서 재사용됩니다.

## 6. 안정성 및 확장성에 대한 고민

- **멱등성(idempotency)을 기본 전제로 삼았습니다.** 모든 쓰기가 upsert 기반이라 같은 구간을 중복 처리해도 결과가 같습니다. 앱 기동 시 세 트리거 지점이 거의 동시에 발화해 백필이 중복 호출되지만, 첫 호출만 실제 작업을 하고 나머지는 이미 gap이 없어 즉시 no-op으로 끝납니다 — 별도의 중복 방지 로직 없이 upsert의 멱등성만으로 자연스럽게 해결됩니다.

- **장애 복구를 최대한 자동화했습니다.** WebSocket 연결이 끊기면 지수 백오프(1초 → 최대 30초, jitter 포함)로 재연결하고, 재연결 성공 시 다운타임 구간을 자동으로 메웁니다. REST 백필 페이지 요청이 실패하면 최대 3회 지수 백오프로 재시도합니다.

- **기동 순서도 명시적으로 보장했습니다.** `docker-compose.yml`에 헬스체크(`db`는 `pg_isready`, `backend`는 `/actuator/health`)를 두고 `depends_on: condition: service_healthy`로 연결해, 백엔드가 실제로 요청을 받을 준비가 되기 전에 프론트엔드(nginx)가 먼저 떠서 502를 반환하는 문제를 막았습니다.

## 7. 대시보드 지표 선택 이유

지표는 '투자 판단'과 '운영 현황 파악' 두 관점으로 나눠 선정했습니다. 전체 근거는 [METRICS.md](METRICS.md)에 정리했고, 핵심만 요약하면 다음과 같습니다.

| 지표                           | 관점                  | 선택 이유                                                                                                                               |
| ------------------------------ | --------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| 현재가 / 24시간 변동률         | 투자 판단             | '지금 얼마고, 오늘 어떻게 움직였는지'는 어떤 트레이딩 대시보드든 가장 먼저 답해야 하는 질문입니다.                                      |
| 24시간 고가/저가               | 투자 판단             | 현재가가 오늘 레인지의 어디쯤 있는지로 상승/하락 압력을 가늠하는 기준선이 됩니다.                                                       |
| 거래량/거래대금 (1분봉, 24시간) | 투자 판단 + 운영 현황 | 가격 변동이 실제 거래를 동반했는지 판단하는 근거이면서, 평소 대비 급증/급감을 운영상 이상 신호로도 활용할 수 있는 이중 목적 지표입니다. |
| 체결건수                       | 투자 판단             | 같은 거래량이라도 소수 대량 주문인지 다수 소액 주문인지 구분해, 거래량 숫자 하나로는 못 보는 체결 패턴을 보완합니다.                    |
